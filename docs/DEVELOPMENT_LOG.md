## 2. 데이터 분석 — 이후 모든 결정의 근거

모델을 만들기 전에 데이터부터 측정했고, 여기서 나온 세 가지가 전략을 결정했습니다.

### 2-1. 이미지 없이 0.5655가 나옵니다

질문+선지 텍스트만으로 TF-IDF + 로지스틱 회귀 (5-fold **GroupKFold**):

```
전체 0.5655   |   카운팅 0.4533   |   기타 0.6244      (랜덤 0.25)
"가장 긴 선지 고르기" 규칙만으로도 0.424
```

원인은 선지 구조 편향입니다. 카운팅 문항에서:

| 값 | 선지로 등장 | **실제 정답** |
|---|---|---|
| 1개 | 19.5% | 21.3% |
| 2개 | 21.5% | **39.3%** |
| 3개 | 22.9% | 16.5% |
| 4개 | 18.7% | 7.6% |

**이 0.5655가 "이미지를 활용하고 있는가"의 판정선**이 되었고, 나중에 앙상블 파트너로도 쓰였습니다.

> ⚠️ **CV 함정**: 한 문항의 선지 4개는 반드시 같은 폴드에 묶어야 합니다.
> 그냥 shuffle하면 0.5206으로 왜곡됩니다. `GroupKFold(groups=문항인덱스)` 필수.

### 2-2. `dev.csv`는 검증셋으로 쓸 수 없습니다

`answer1~5`는 정답이 아니라 **교육생이 제출한 응답**입니다.

```
응답자 간 pairwise 일치도   37.5%   (랜덤 25%)
5인 만장일치               1 / 4,413 = 0.02%
카운팅 문항 비율            71.3%   (test는 33.8%)
```

만장일치 비율이 특히 이상합니다. "5명이 독립적으로 답하고 각자 확률 p로 정답"이면
만장일치 비율은 `p⁵ + 3·((1-p)/3)⁵ ≥ 0.0039` (p=0.25에서 최소)인데, 실제는 0.00023 —
**어떤 p를 넣어도 최소 17배 차이**입니다. 독립 응답 모델 자체가 성립하지 않습니다.

→ 생성 구조를 알 수 없으므로 **검증에 쓰지 않기로** 결정.

### 2-3. train과 test는 분포가 같습니다

```
카운팅 비율   train 34.4%  /  test 33.8%  /  dev 71.3%
정답 위치     a 24.9 / b 24.9 / c 25.8 / d 24.3 %
```

→ **train을 `정답위치 × 문항유형`으로 층화 분할**해 홀드아웃 609건을 만들었습니다.
이 판단이 이후 모든 실험의 신뢰도를 뒷받침했습니다.

### 2-4. 실무 함정

- **제출 id는 확장자를 포함합니다** (`test_0001.jpg`). Overview 표의 `test_0001`은 축약 표기 — 그대로 쓰면 5,074건 전부 오채점
- test 이미지 5,074장 전수 디코딩 검사: **누락 0 / 손상 0 / 전부 RGB**
- train↔test에 **동일 이미지 87장**(MD5 일치). 질문까지 같아 정답 이식이 가능한 건 24건

## 3. 베이스라인 진단

제공된 베이스라인에서 발견한 문제들입니다.

### 🔴 치명적

**① 라벨 마스킹 없음**
```python
enc["labels"] = enc["input_ids"].clone()   # 프롬프트·이미지패드 토큰까지 전부 학습
```
정답 글자 1개가 300여 토큰 중 하나라 학습 신호가 사실상 소멸.
`[Epoch 1] valid loss 5.5235`는 "한국어 질문 문장 재생성 능력"을 재고 있었을 뿐입니다.

**② `generate()` + 문자열 파싱**
```python
out = model.generate(**inputs, max_new_tokens=2)   # 30~60분
...
return "a"                                          # 파싱 실패 시 무조건 'a'
```
→ **마지막 위치 logits에서 `a`/`b`/`c`/`d` 4개만 비교**로 교체.
파싱 실패가 원천적으로 불가능해지고, 추론이 30~60분 → 수 분으로.

**③ 5,073개 중 200개만 학습** — optimizer step이 45회뿐

**④ 검증이 accuracy가 아니라 loss** — ①번 때문에 모델 선택 신호로 무의미

### 🟡 정합성

| 문제 | 수정 |
|---|---|
| `GradScaler`(fp16 전용) + `autocast(bfloat16)` | GradScaler 제거, bf16 통일 |
| `bnb_4bit_compute_dtype=float16` vs autocast bf16 | 양쪽 bf16으로 |
| `prepare_model_for_kbit_training` 후 `gradient_checkpointing_enable()` 재호출 → reentrant 복귀 | `use_reentrant=False` 일원화 |
| 마지막 자투리 배치 gradient 폐기 | `step % ACC == 0 or is_last` |
| `/content/`, `content/submission.csv` (Colab 경로) | Windows 경로 + 제출 검증 |

### 학습·추론 정합성 설계

```
학습:  [프롬프트 + assistant 헤더] + "b"   ← 마지막 토큰 1개에만 loss
추론:  [프롬프트 + assistant 헤더]        ← 마지막 위치 logits에서 a~d 비교
```

정답 뒤에 `<|im_end|>`를 붙이지 않아 **단일 토큰 4지 분류**가 되고, 학습과 추론이 완전히 일치합니다.

## 4. 성능 개선 여정

### 4-1. 해상도 (+7.8%p 중 상당 부분)

```
384px  0.7307   (카운팅 0.571)
512px  0.7455   (카운팅 0.576)
640px  0.7504   (카운팅 0.619)      홀드아웃 609건, ±2.0%p
```

`IMAGE_PX`는 **프로세서 설정일 뿐이라 모델 재로드가 불필요**합니다.
덕분에 3개 해상도 비교를 9분 만에 끝냈습니다. 640px 이후는 수확 체감.

### 4-2. 모델 크기 — 가장 큰 단일 이득 (+6.1%p)

| 홀드아웃 | 3B bf16 | **7B 4bit** |
|---|---|---|
| 전체 | 0.7504 | **0.8276** |
| 카운팅 | 0.6190 | 0.6857 |
| 기타 | 0.8195 | 0.9023 |

16GB에서 7B는 bf16(16.6GB)이 안 들어가므로 **4bit 필수**.
반대로 3B는 4bit가 오히려 손해였습니다 — 베이스라인 로그에
`bitsandbytes ... falling back to slower implementation` 경고가 있었고, bf16이 더 빠르고 정확했습니다.

### 4-3. 텍스트 모델 블렌딩 (+1.5%p)

VLM과 텍스트 전용 모델은 **서로 다른 신호**를 씁니다. 확률을 로그공간에서 가중 기하평균:

```
P = P_vlm^α · P_text^(1-α)        α = 0.75
```

블렌딩용 텍스트 모델은 별도로 강화했습니다 (0.5714 → 0.6355):
char n-gram + word n-gram + **수작업 피처**(선지 길이·숫자값·오름차순 순위·"2로부터의 거리"·`둘 다`/`없음` 포함 여부), 카운팅은 GBDT / 기타는 TF-IDF.

**이득이 카운팅에 집중**됐습니다 (0.6857 → 0.7143). 예측 가능했던 결과입니다 —
카운팅에서 텍스트 모델(0.6238)과 VLM(0.6857)의 격차가 6%p뿐이라 앙상블 효과가 가장 큰 지점이었습니다.

### 4-4. 저신뢰 구간 선지 순서 TTA (+1.0%p)

신뢰도 5분위 분석에서 오답이 극단적으로 편중돼 있음을 확인:

```
Q1 (conf 0.33~0.55)  정확도 0.525  오답 58건   ← 전체 오답 96건의 60%, 이 구간의 75%가 카운팅
Q2 (0.56~0.75)       0.811         23건
Q3 (0.76~0.93)       0.893         12건
Q4~Q5 (0.93~1.00)    0.99~1.00      2건
```

그리고 위치 편향이 측정됐습니다:
```
예측  a 140 / b 152 / c 188 / d 129
실제  a 152 / b 152 / c 157 / d 148     ← c를 31건 과다 선택
```

→ **저신뢰 구간만** 선지 순서를 순환 치환해 재추론하고 확률 평균.
전체 재추론이 99분인데 하위 40%는 24분이라 시간 예산 안에 들어옵니다.

```
대상 122건  0.5246 → 0.5738  (+4.9%p)
전체 609건  0.8424 → 0.8522  (+0.99%p)
```

**하이퍼파라미터를 사전 고정**(치환 1회, 가중치 0.5)해 선택 편향이 없는 추정치입니다.

### 4-5. 중복 이미지 정답 이식 (+0.10%p)

train↔test 동일 이미지 87장 중 질문까지 같은 30건에서, 정답 **텍스트**를 test 선지에서 찾아
글자를 재매핑 → 24건 확정. 그중 5건이 실제 개선. 비용 0, 위험 0.

## 5. 실패한 실험 — 기록해두는 이유

성공한 것보다 이쪽이 더 많은 걸 알려줬습니다.

### ❌ 카운팅 숫자 직접 스코어링

**가설**: 모델에게 "① 개수를 센다 ② 그 개수와 일치하는 글자를 찾는다" 두 가지를 시키는데,
②의 간접 단계를 제거하면 나아질 것.

**근거는 충분했습니다** — 카운팅 선지의 84.5%가 `N개` 형태, **선지 숫자 중복률 0.00%**
(숫자만 맞히면 선지가 유일하게 결정), 정답의 96.3%가 한 자리 숫자.
선지를 보여주지 않고 "숫자 한 글자만 출력하세요"로 물은 뒤 해당 숫자 토큰들만 비교.

**결과**: 숫자 0.6818 < 글자 0.6919. **가설 기각.**
모델은 글자를 찾는 데서 실패하는 게 아니라 **애초에 개수를 세지 못합니다.**

### ❌ 저신뢰 문항 2지선다 재질의

**가설**: 하위 20%에서 top-1 정확도는 0.525인데 **top-2 포함률은 0.836**.
후보를 2개로 좁히는 건 되니, 오답 2개를 지우고 2지선다로 다시 물으면 개선될 것.

**결과**: 대상 -9.0%p, 전체 **-1.81%p**. 크게 악화.

**원인 분석**: 2지선다 결과로 덮어쓰면서 **그 두 선지에 대한 텍스트 모델의 판단을 통째로 버렸습니다.**
이 구간의 75%가 카운팅 = 블렌딩 이득이 가장 컸던 영역이라, 이득을 정확히 제거한 셈입니다.
여기에 4지선다 맥락 자체가 정보를 준다는 요인도 겹친 것으로 보입니다.

→ 이 교훈을 반영해 TTA에서는 **VLM 확률에만 TTA를 적용하고 텍스트 블렌딩을 뒤에 다시 얹었고**, 성공했습니다.

### ❌ 노이즈였던 것들

| 시도 | 홀드아웃 | 판정 |
|---|---|---|
| 사전분포 균등 교정 (tau) | +0.16%p | 노이즈 |
| dev pseudo-label + 유형별 α | 탐색 시 +0.65%p → **재구성 시 +0.16%p** | **선택 편향** |
| 질문+선지 정확 일치 조회 | 0.5200 (VLM 0.8276) | 무용 |
| 교정+블렌딩 2차원 격자 탐색 | +1.81%p (88개 조합) | 채택 안 함 |

**"홀드아웃 609건에서 +1.5%p 미만이면 채택하지 않는다"** 는 기준을 세워두고 지켰습니다.
609건에서 1%p는 6문항이고, 표준오차가 ±2.0%p입니다.

단 이 기준은 **탐색으로 고른 값**에만 적용했습니다. TTA처럼 하이퍼파라미터를 사전 고정한
비편향 추정치는 +0.99%p여도 채택했습니다.

## 6. 엔지니어링 함정

단일 GPU / Windows 환경에서 실제로 시간을 잡아먹은 것들입니다.

**VRAM이 넘치면 Windows WDDM이 조용히 시스템 RAM으로 스필합니다**
```
정상        3.75 s/batch
스필 발생   7.65 s/batch     (python 프로세스 Commit 21GB로 확인)
```
그래서 `USE_GRAD_CKPT`를 끄는 건 오히려 손해였습니다. 메모리를 아껴야 빨라집니다.

**`device_map="auto"`는 VRAM이 모자라면 말없이 오프로드합니다**
```
RuntimeError: Function MmBackward0 returned an invalid gradient at index 1
              - expected device meta but got cuda:0
```
같은 커널에서 모델을 두 번 로드해 VRAM이 찼고, accelerate가 일부 레이어를 `meta`로 남겼습니다.
→ `device_map={"": 0}`으로 고정해 **조용한 오프로드 대신 명시적 OOM**이 나게 했습니다.
로드 직후 `meta`/`cpu` 파라미터 검사도 추가했습니다.

**VSCode가 외부에서 수정한 노트북을 자기 버퍼로 덮어씁니다**
열려 있는 `.ipynb`를 밖에서 고치면 VSCode 저장 시 되돌아갑니다. 반드시 닫거나 "디스크에서 다시 로드".

**같은 커널에서 셀 재실행 시 모델 이중 로드** → 로드 전 `del` + `empty_cache()` + VRAM assert 추가.

**스모크 테스트가 본 실행을 오염시킬 수 있습니다**
설정을 파일명에 넣어(`RUN_TAG`) 어댑터·제출물을 실행별로 분리했습니다.

- 선지 `a`~`d`가 각각 **단일 토큰**인지 assert
- 마스킹 후 **학습 대상 토큰이 정확히 1개**이고 실제 정답과 일치하는지 assert
- 모델 로드 전후 VRAM 검사 + `meta`/`cpu` 오프로드 검사
- 학습 전 **zero-shot 성능 측정** → 학습이 모델을 망쳤는지 판별
- 제출 파일 4중 검증 (행 수 / id 순서 / 결측 / 허용값)
- `SMOKE_TEST=True` 로 96/32/64건 축소 실행 → 5분 안에 전 과정 검증

## 9. 남은 과제

### ✅ 파인튜닝 — 마감 직전에 검증했고, 효과가 있습니다

작업 대부분의 기간 동안 파인튜닝은 **한 번도 끝까지 돌아본 적이 없는 상태**였습니다.
베이스라인은 라벨 마스킹 버그로 학습이 망가져 있었고, v2에서는 `meta` 디바이스 오류와
VRAM 스필로 각각 batch 17·14에서 중단됐으며, 이후 시간 제약으로 `SKIP_TRAIN`으로 전환했습니다.

이 과정에서 출력된 `best (학습후) ... (+0.00%p)` 를 **"파인튜닝이 효과 없다"로 잘못 해석**하고
한동안 다른 방향만 파고들었습니다. 실제로는 `best_acc = zs["acc"]`가 그대로 출력된 것,
즉 **학습이 실행되지 않았다**는 뜻이었습니다.

마지막에 33분을 확보해 검증한 결과 (7B 4bit / 640px / batch 1 / accum 8 / lr 1e-4,
홀드아웃 앞 400건 짝지은 비교):

```
zero-shot    0.8300   (카운팅 0.6794)
파인튜닝 후   0.8575   (카운팅 0.7252 / 기타 0.9219)
             +2.75%p          +4.58%p
```

**104 optimizer step / 832샘플만으로** 나온 수치입니다 (train 4,464개의 19%).
학습 loss는 0.211까지 하강했습니다 (랜덤 = ln 4 = 1.386).

특히 **카운팅이 +4.6%p**로 가장 크게 올랐습니다. 오늘 시도한 카운팅 개선안 중
해상도(+4.8%p)와 함께 가장 효과가 컸고, TTA(+4.9%p, 저신뢰 구간 한정)와 달리
**전 구간에 적용됩니다.**

> **교훈**: "실행되지 않은 것"과 "효과가 없는 것"을 구분하지 못하면 가장 좋은 방향을
> 스스로 닫아버립니다. 출력 로그의 `0.00%p`가 어디서 나온 값인지 추적했어야 했습니다.

### 왜 0.92에 도달하지 못했나

```
0.34 × 카운팅 0.714  +  0.66 × 기타 0.910  =  0.845
```

기타는 0.91로 한계에 근접했고 **병목은 카운팅 하나**입니다. 카운팅 개선을 네 방향으로 시도했고
전부 같은 결론을 가리켰습니다:

| 시도 | 결과 |
|---|---|
| 해상도 384→640 | 카운팅 +4.8%p, 이후 수확 체감 |
| 숫자 직접 스코어링 | 글자 방식보다 낮음 |
| 2지선다 재질의 | -9.0%p |
| 선지 순서 TTA | +4.9%p (유일한 성공) |

결정적 관찰은 이것입니다 — **이미지를 전혀 보지 않는 텍스트 모델이 카운팅에서 0.6238,
7B VLM이 0.6857.** 격차가 6%p뿐입니다.

**모델이 실제로 개수를 세는 것이 아니라 선지 구조를 이용하고 있습니다.**
선지 제시 방식을 어떻게 바꿔도 없는 능력이 생기지는 않았습니다.
이를 넘으려면 더 큰 모델이나 Chain-of-Thought 추론이 필요한데, 단일 토큰 로짓 비교 방식과는
양립하지 않고 생성 방식은 시간 예산을 초과했습니다.

### 10-1. 파인튜닝을 test에 반영 (LB 0.84430 → 0.86322)

1일차에 홀드아웃으로만 검증했던 어댑터를 test 5,074건에 적용했습니다.
추가로 **파인튜닝 확률과 zero-shot 확률을 단순 평균**하면 +0.66%p가 더 나왔습니다
(zero-shot test 확률은 이미 저장돼 있어 **추가 계산 비용 0**).

홀드아웃이 예측한 개선폭 +2.00%p, 실제 LB 개선폭 +1.89%p — **오차 0.11%p**.

> **절대값이 아니라 개선폭을 보세요.** 홀드아웃 400건은 LB보다 약 1.1%p 낙관적이지만
> (609건은 오프셋 ~0), **짝지은 비교의 개선폭은 거의 그대로 전이**됩니다.
> 이후 모든 판단을 609건 홀드아웃의 개선폭으로 했습니다.

### 10-2. 카운팅 문항에만 고해상도 — 실패, 그리고 왜 속았는가

병목이 카운팅 하나라는 진단(§9)에 따라, 파인튜닝 어댑터를 해상도만 바꿔 재측정했습니다.

| 해상도 | 전체 | **카운팅** | 기타 |
|---|---|---|---|
| 640px (어댑터 학습 해상도) | 0.8489 | 0.7190 | 0.9173 |
| **768px** | 0.8670 | **0.7810** | 0.9123 |
| 896px | — | 0.7476 | — |

768px가 최적점인 **역U자**입니다. 픽셀이 많아 세기 쉬워지는 이득과, 어댑터 학습
분포에서 멀어지는 손해가 균형을 이루는 지점입니다.

핵심은 **해상도가 카운팅에만 듣는다**는 것입니다. 짝지은 검정으로 확인했습니다:

| 부분 | 고쳐짐 / 망가짐 | p값 |
|---|---|---|
| 카운팅 210건 | 19 / 6 | **0.0146** |
| 기타 399건 | 3 / 5 | 0.73 |

그래서 전부 768px로 바꾸면 기타가 손해를 봐 순이득이 반토막 납니다(+0.82%p).
**문항 유형별로 나누는 것**이 정답이었습니다:

| 구성 | 전체 | 카운팅 | 기타 |
|---|---|---|---|
| 전부 640px (LB 0.86322) | 0.8621 | 0.7333 | 0.9298 |
| 전부 768px | 0.8703 | 0.7857 | 0.9148 |
| **카운팅=768 / 기타=640** | **0.8801** | 0.7857 | 0.9298 |

당시에는 이렇게 판단했습니다 — *"1일차 3B 스윕이 같은 패턴을 예측했으니 사후
탐색이 아니다. 분할 기준도 튜닝한 임계값이 아니라 기존 정규식이다."*

**제출 결과 LB 0.86164. 기준선 0.86322보다 낮았습니다.**
홀드아웃 예측 +1.81%p, 실제 −0.16%p.

#### 왜 틀렸는가

오프셋 이력이 답을 말해줍니다.

| 구성 | 평가한 구성 수 | 홀드아웃 | LB | 오프셋 |
|---|---|---|---|---|
| zs+텍스트 | α 1차원 탐색 | 0.8424 | 0.84430 | +0.19%p |
| ft+zs+텍스트 | 6개 중 선택 | 0.8621 | 0.86322 | +0.11%p |
| 카운팅 768px | **30개 넘게 평가** | 0.8801 | 0.86164 | **−1.85%p** |

같은 609건 위에서 해상도 3개, 앙상블 조합 8개, 하이브리드 6개, 블렌딩
가중치·온도·α까지 30개가 넘는 구성을 평가하고 **그중 최대값을 골랐습니다.**
표준오차 ±2.0%p에서 N개 중 최대를 고르면 대략 `±2.0%p × √(2 ln N) / 2` 만큼
부풀려집니다. N=30이면 +1.8%p — 관측된 오프셋과 정확히 일치합니다.

McNemar p=0.0347도 무효입니다. **선택한 뒤 계산한 p값**이라 다중비교 보정이
필요하고, 30개 기준이면 p≈1.0입니다.

#### 진짜 교훈

"메커니즘이 예측한 것이라 탐색이 아니다"라는 논리가 함정이었습니다.
3B 스윕은 **640px까지만** 보여줬을 뿐, 7B 파인튜닝 모델의 768px나 유형별 분할을
예측한 게 아닙니다. 그럴듯한 서사는 다중비교를 상쇄해주지 않습니다.
**사전에 적어두지 않은 예측은 사후 설명입니다.**

이 프로젝트에는 원래 "탐색으로 고른 값은 +1.5%p 미만이면 채택 금지"라는 규칙이
있었습니다. +1.81%p라 형식상 통과했지만, 그 규칙은 **몇 개 중에서 골랐는지**를
전제로 한 것이었고 30개는 그 전제를 벗어납니다. 규칙을 아래처럼 고쳤습니다.

| 평가한 구성 수 | 채택 기준 |
|---|---|
| 사전에 하나 지정 | +1%p |
| 5개 이하 | +1.5%p |
| 10개 초과 | **그 홀드아웃으로는 판단 불가** — 건드리지 않은 데이터로 재측정하거나 제출로 확인 |

역설적이지만 **제출 1회가 가장 싸고 정직한 검증**이었습니다.

### 10-3. 추론 단계 실험 — 7전 7패

2일차에 추론 시점에서 할 수 있는 개선을 7가지 시도했습니다.

| 시도 | 결과 |
|---|---|
| dev→test 정답 이식 | 신규 2~3건 (5,074건 중 0.05%p) |
| 텍스트 모델 v2 (선지별 이진분류) | 0.6141 < 기존 0.6355 |
| 블렌딩 정제 (가중치·기하평균·온도·α) | 최대 +0.49%p |
| 선지 순서 TTA (파인튜닝 후) | **−0.16%p** |
| 좌우반전 TTA | +0.33%p |
| 카운팅 문항 768px | 홀드아웃 +1.81%p → **LB −0.16%p** |
| 카운팅 Chain-of-Thought | **−8.57%p (p=0.027)** |

**전부 실패했습니다.** 처음에는 "같은 정보를 다르게 조합한 5개는 실패하고, 더 많은
정보를 준 1개는 성공했다"는 깔끔한 패턴으로 읽었지만, 그 1개도 LB에서 무너졌습니다.

남는 결론은 더 단순합니다. **이 문제에서 실제로 통한 것은 모델 자체를 키우거나
(3B→7B) 학습시키는 것(파인튜닝)뿐이었습니다.** 추론 시점의 재조합·재가공은
해상도까지 포함해 전부 노이즈였습니다.

### 10-4. CoT가 오히려 나빴다는 것의 의미

§9는 "모델이 개수를 세는 게 아니라 선지 구조를 이용한다"고 진단하며, 이를 넘으려면
Chain-of-Thought가 필요하다고 적었습니다. 실행해봤고 **−8.57%p로 유의하게 나빴습니다**
(고쳐짐 21 / 망가짐 39, p=0.027).

생성 자체는 완벽했습니다. 모델은 실제로 단계별로 셉니다 —
*"1번 병, 2번 병, 3번 병, 4번 병, 그리고 5번 병이 보입니다"*.
평균 92자, 210건 중 199건이 형식을 지켰습니다. 그런데 답은 더 자주 틀립니다.

**명시적 계수가 암묵적 단일 토큰 판단보다 부정확합니다.** 진단을 한 겹 수정해야 합니다:
모델에게 없는 것은 *세는 방법*이 아니라 *세는 능력*입니다. 선지 구조를 이용하는
편법이 실제 계수보다 정확했기 때문에, 편법을 막고 제대로 세게 하면 오히려 나빠집니다.

부수적으로 관찰된 것 하나 — 파인튜닝 어댑터는 CoT 지시를 **무시합니다.** 프리필 없이
생성시키면 45%가 추론 전에 정답 글자부터 뱉었습니다. 단일 글자 출력으로 학습한
어댑터가 프롬프트 지시를 이깁니다. 파인튜닝이 모델의 행동을 얼마나 강하게 고정하는지
보여주는 사례입니다.

특히 **선지 순서 TTA가 파인튜닝 후에 효과를 잃은 것**이 시사적입니다.
zero-shot에서는 +0.98%p였는데 파인튜닝 확률에서는 −0.16%p입니다.
§9의 "모델이 개수를 세는 대신 선지 구조를 이용한다"는 진단이 맞다면,
**파인튜닝이 그 의존을 실제로 줄였다**는 직접 증거입니다.

### 10-5. 2일차의 결론

| 방향 | 결과 |
|---|---|
| 모델 키우기 (3B → 7B) | +6.1%p |
| 파인튜닝 104 step | +1.89%p (LB) |
| 추론 시점 재조합·재가공 7종 | 전부 노이즈 또는 악화 |

**이 문제에서 통한 것은 모델에게 더 많이 가르치는 것뿐이었습니다.**
