## 2. 잘한 점 (Keep)

### ① 모델을 만들기 전에 데이터를 먼저 쟀습니다

- **텍스트만으로 0.5655** (랜덤 0.25) — 이미지를 보지 않는 기준선을 먼저 세웠습니다.
  "모델이 이미지를 실제로 쓰고 있는가"의 판정선이 됐고, 나중에는 블렌딩 파트너(홀드아웃 +1.5%p)가 됐습니다.
- **`dev.csv` 를 검증에 쓰지 않은 것** — 교육생 응답이라는 점을 수치로 확인했습니다
  (응답자 간 일치도 37.5%, 만장일치는 독립 응답 모델의 이론 최솟값보다 17배 낮음, 카운팅 비율 71% vs test 34%).
  그대로 썼다면 리더보드와 무관한 숫자를 보며 판단했을 것입니다.
- **train을 `정답 위치 × 문항 유형` 으로 층화 분할한 홀드아웃 609건** — 사전에 정한 구성에서는
  리더보드와 ±0.2%p 이내로 맞았고, 이후 모든 판단의 기준이 됐습니다.
- 이 과정에서 CV 함정(한 문항의 선지 4개를 같은 폴드에 묶지 않으면 0.5206으로 왜곡)도 스스로 잡았습니다.

### ② 베이스라인을 그대로 쓰지 않고 진단했습니다

라벨 마스킹 없음, `generate` 후 파싱 실패 시 무조건 `a`, 5,073개 중 200개만 학습, loss로 검증 —
네 가지 치명적인 문제를 찾아 고쳤습니다. 특히 **정답 위치의 a/b/c/d 로짓 4개만 비교**하고
**정답 1토큰에만 loss** 를 걸어 학습과 추론을 정확히 일치시킨 것이 이후 모든 개선의 바탕이 됐습니다.
이것만으로 파싱 실패 0, 추론 시간 30~60분 → 수 분, Public +7.84%p (bf16·640px 변경 포함).

### ③ 확률 파일 중심으로 파이프라인을 짰습니다

모든 모델의 출력을 `.npy` 확률 파일로 저장했습니다. 덕분에 앙상블·블렌딩 실험을 GPU 없이 수 초 만에
반복할 수 있었고, **파인튜닝 + zero-shot 평균(+0.66%p)** 을 추가 계산 비용 0으로 찾았습니다
(99분짜리 zero-shot test 확률이 이미 있었기 때문).

### ④ 실패를 원인까지 기록하고 다음 설계에 반영했습니다

저신뢰 문항 2지선다 재질의(−1.81%p)가 실패한 원인을 "그 두 선지에 대한 텍스트 모델의 판단까지 통째로 버렸다"로
분석했고, 바로 다음 실험인 선지 순서 TTA에서는 **VLM 확률에만 TTA를 적용하고 블렌딩을 뒤에 다시 얹어**
성공했습니다(홀드아웃 +0.99%p). 채택 규칙도 실패를 겪을 때마다 고쳐 썼습니다.

### ⑤ "조용히 잘못된 결과"를 막는 장치를 넣었습니다

- 선지 `a`~`d` 가 각각 단일 토큰인지, 마스킹 후 학습 대상 토큰이 정확히 1개인지 assert
- 모델 로드 후 `meta`/`cpu` 오프로드 검사, 어댑터 로드 후 `lora_B` 절대합 검사
- `logits_to_keep=1` 최적화가 원래 결과와 같은지 매번 비교
- 새 확률 파일을 만들면 **"예측이 바뀌어야 할 비율"** 을 홀드아웃 예측치와 대조
  (0%면 어댑터 미반영, 25% 이상이면 정렬 오류)
- 제출 파일 4중 검증, 2분 단위로 재개 가능한 추론, Colab에서 옵티마이저 상태까지 저장하는 학습

### ⑥ 제한된 장비로 7B를 끝까지 돌렸습니다

16GB에서 4bit QLoRA로 7B를 학습했고, 8GB 노트북은 추론 전용(배치를 줄여도 `logits_to_keep` 으로
데스크탑과 같은 속도), 학습은 Colab T4로 나눴습니다. 세 환경을 오가는 동안 옮길 때마다 인수인계 문서를
남겨 맥락이 끊기지 않게 했습니다.

### ⑦ 공개 전에 재현성을 검증하고, 차이를 숨기지 않았습니다

정리한 스크립트가 실제 제출 파일을 5,074행 전부 똑같이 만드는지 확인했습니다.
텍스트 모델 학습 코드를 잃어버려 재구현본(0.6141)이 원본(0.6355)과 다르다는 점도 README에 그대로 적었습니다.

## 3. 아쉬운 점 (Problem)

### ① 파인튜닝을 "효과 없음"으로 착각해 가장 늦게 열었습니다

베이스라인의 학습은 라벨 마스킹 버그로 망가져 있었고, 고친 뒤에도 `meta` 디바이스 오류와 VRAM 스필로
batch 17·14에서 중단됐습니다. 이후 학습을 건너뛰도록 바꿨는데, 그때 출력된 `best (학습후) ... (+0.00%p)` 를
**"파인튜닝은 효과가 없다"로 읽었습니다.** 실제로는 학습이 **실행되지 않았다**는 뜻이었습니다.

1일차 마지막에 33분을 확보해 처음으로 끝까지 돌려보니 104 step만으로 홀드아웃 +2.75%p(카운팅 +4.58%p)였습니다.
이 프로젝트에서 효과가 있던 건 모델 키우기와 학습뿐이었는데, 정작 그 축에 쓴 시간이 가장 적었습니다.

### ② 추론 단계 튜닝에 시간을 너무 많이 썼습니다

2일차 추론 단계 실험은 7전 7패였습니다(TTA 2종, 해상도, CoT, 블렌딩 정제, 텍스트 모델 v2, 정답 이식).
블렌딩 가중치·온도·α를 훑어서 얻은 최대치도 +0.49%p, 609건에서 3문항 수준의 노이즈였습니다.
반면 학습을 104 → 300 step으로 늘리자 홀드아웃 +2.79%p, 그중 카운팅은 **+7.15%p** 가 올랐습니다.
어떤 추론 기법으로도 움직이지 않던 병목이 학습량을 늘리자 크게 움직였습니다.

### ③ 가장 좋은 결과를 제출하지 못했습니다

300 step 어댑터는 홀드아웃 609건에서 **0.8900** 이었습니다. 제출 구성과 같은 조합에 어댑터만 바꾼
사전 지정 단일 구성이라, 609건 홀드아웃이 리더보드와 ±0.2%p로 맞았던 이력대로라면 0.89 근처를 기대할 수 있었습니다.
하지만 test 추론(약 60분)이 44%에서 중단된 뒤 제출로 이어지지 못했고, 최종 점수는 104 step 어댑터의 0.86322로 남았습니다.
①②에서 학습 연장을 늦게 결정한 것이 그대로 이어진 결과입니다.

### ④ 같은 홀드아웃을 과하게 탐색해 선택 편향에 속았습니다

해상도 3개, 앙상블 조합 8개, 하이브리드 6개, 블렌딩 파라미터까지 **같은 609건 위에서 30개 넘는 구성**을 평가하고
그중 최대값인 "카운팅만 768px"를 제출했습니다. 홀드아웃 +1.81%p → 리더보드 **−0.16%p** 였습니다.

당시에는 "1일차 3B 해상도 실험이 예측한 메커니즘이니 사후 탐색이 아니다"라고 스스로를 설득했습니다.
같은 실수를 코드에도 넣었습니다. CoT 실험 스크립트의 자동 판정을 `max(CoT 단독, 혼합)` 에 걸어두는 바람에,
사전에 정한 지표(CoT 단독, −8.57%p)는 실패였는데도 "채택"이 출력됐습니다.

### ⑤ 결과를 만든 코드를 노트북 세션에만 뒀습니다

최종 제출에 쓴 텍스트 모델(0.6355)의 학습 코드를 노트북 세션에만 두었다가 잃어버렸습니다.
결과 파일은 남았지만 처음부터 다시 돌리면 최종 점수를 정확히 재현할 수 없습니다.
노트북 전역 변수에 기대어 붙여넣던 실험 셀들도 지금은 단독으로 실행되지 않습니다.

### ⑥ 에러 없이 느려지거나 멈추는 문제에 시간을 잃었습니다

| 증상 | 원인 |
|---|---|
| Colab T4 학습 161 s/step (196 step에 8시간 43분이 표시됨) | `is_bf16_supported()` 가 에뮬레이션도 True → T4에서 bf16을 소프트웨어로 실행. fp16으로 바꾸니 38 s/step |
| 스크립트가 에러 없이 멈춤 (약 8분 손실) | 캐시 경로 설정보다 `transformers` 를 먼저 import → 16GB 재다운로드 대기. 진행 표시는 파이프 버퍼에 갇혀 안 보임 |
| 학습이 갑자기 2배 느려짐 | Windows WDDM이 VRAM 초과분을 시스템 RAM으로 조용히 스필 |
| 시간 추정 3배 오차 | `s/it` 가 샘플당이 아니라 배치당 값이었음 |

## 4. 배운 점 (Learned)

### 검증에 대해

1. **검증셋은 리더보드를 맞히는지 확인한 뒤에 믿는다.** 홀드아웃과 리더보드의 차이(오프셋)를 제출마다
   기록해 두니, 어떤 숫자를 믿어도 되는지가 보였습니다.

2. **홀드아웃의 신뢰도는 "몇 개 중에서 골랐는가"로 정해진다.** 표준오차 ±2.0%p인 홀드아웃에서 N개 중
   최대를 고르면 대략 `2.0%p × √(2 ln N) / 2` 만큼 부풀려집니다. N=30이면 +1.8%p — 관측된 차이와 거의 같았습니다.

   | 구성 | 어떻게 골랐나 | Public − 홀드아웃 |
   |---|---|---|
   | 7B zero-shot | 사전 고정 | +0.14%p |
   | + 텍스트 블렌딩 | α 1차원 탐색 | +0.19%p |
   | + 파인튜닝·zs 평균 | 6개 중 선택 | +0.11%p |
   | 카운팅만 768px | 30개 이상 중 최대 | **−1.85%p** |

3. **절대값보다 개선폭을 본다.** 홀드아웃 400건은 리더보드보다 약 1.1%p 낙관적이었지만,
   같은 문항끼리 짝지어 비교한 개선폭(+2.00%p)은 실제 개선폭(+1.89%p)과 0.11%p 차이로 맞았습니다.

4. **그럴듯한 설명은 다중비교를 상쇄하지 않는다.** 선택한 뒤에 계산한 p값(0.035)은 보정하면 의미가 없었고,
   미리 적어두지 않은 예측은 사후 설명일 뿐이었습니다. 판정 기준은 실행 전에, 하나로 정해야 합니다.

5. **제출 한 번이 가장 싸고 정직한 검증일 때가 있다.** 홀드아웃을 너무 많이 썼다면 그 홀드아웃으로 더 고민하지 말고 제출로 확인하는 편이 낫습니다.

### 모델링에 대해

6. **이 문제에서 통한 건 모델에게 더 가르치는 것뿐이었다.** 3B → 7B(+6.1%p), 파인튜닝(+1.89%p), 학습 연장(홀드아웃 +2.79%p).
   추론 시점의 재조합·재가공은 해상도까지 포함해 전부 노이즈였습니다.

7. **없는 능력은 방법으로 만들 수 없다.** 카운팅에서 이미지를 안 보는 텍스트 모델이 0.62, 7B VLM이 0.69 —
   모델은 개수를 세기보다 선지 구조를 이용하고 있었습니다. Chain-of-Thought로 단계별로 세게 했더니
   형식은 완벽했지만 정확도는 −8.57%p(p=0.027)였습니다. 부족했던 건 *세는 방법*이 아니라 *세는 능력*이었습니다.

8. **기법의 효과는 모델 상태에 달려 있다.** 선지 순서 TTA는 zero-shot에서 +0.99%p였지만 파인튜닝 후에는 −0.16%p였습니다.
   파인튜닝이 선지 위치 편향을 이미 흡수했기 때문입니다. 단일 글자 출력으로 학습한 어댑터는 CoT 지시도 무시하고
   45%가 정답 글자부터 출력했습니다. 파인튜닝은 모델의 행동을 생각보다 강하게 고정합니다.

9. **객관식이면 생성할 필요가 없다.** 정답 위치의 로짓만 비교하면 파싱 실패가 사라지고 수십 배 빨라집니다.
   학습 목표와 추론 방식을 정확히 맞추는 것이 작은 트릭 여러 개보다 컸습니다.

10. **서로 다른 신호를 보는 모델끼리 앙상블하면 효과가 크다.** 텍스트 모델은 이미지를 보지 않는데도 블렌딩으로 +1.5%p를 더했고,
    이득은 두 모델의 실력 차가 가장 작은 카운팅에 몰렸습니다.

### 엔지니어링에 대해

11. **"실행되지 않음"과 "효과 없음"은 다르다.** 로그에 찍힌 숫자가 어디서 온 값인지 추적해야 합니다.
    `+0.00%p` 한 줄을 의심하지 않은 대가가 이번 대회에서 가장 컸습니다.

12. **조용한 실패보다 명시적인 실패가 낫다.** `device_map="auto"` 의 조용한 오프로드보다 `{"": 0}` 의 OOM이,
    "bf16 지원함"이라는 답보다 compute capability로 직접 고른 dtype이 안전했습니다.

13. **결과만큼 결과를 만든 코드도 산출물이다.** 확률 파일은 남았는데 코드가 없어서 재현이 끊겼습니다.

|---|---|
| 파인튜닝을 끝까지 돌려본 적 없이 다른 방향을 팠다 | **첫날 몇 시간 안에 축소 데이터로 학습 → 추론 → 제출 전 과정을 한 번 완주**한다. 학습 로그에는 step 수·loss 변화·가중치 변화량을 함께 찍어 "실행됐다"는 것부터 증명한다 |

| 텍스트 모델 코드를 잃어버렸다 | 노트북은 탐색용으로만 쓰고, **결과를 만든 코드는 바로 `.py` 로 옮겨 커밋**한다. 확률 파일 옆에 생성 명령과 커밋 해시를 남긴다 |

### 이 문제를 다시 푼다면 해볼 것

- **1 epoch(558 step) 이상 학습** — 104 → 300 step에서 +2.79%p였으므로 가장 먼저 해볼 방향입니다.
- 300 step에서는 zero-shot 평균이 더 이상 도움이 되지 않았습니다(파인튜닝 단독 + 텍스트 0.8933 > zs 평균 포함 0.8900).
  새 어댑터마다 **zero-shot 제거를 단일 가설로 사전 지정**해 확인합니다.
- **다른 계열 VLM을 앙상블에 추가** — 같은 모델의 두 상태를 평균한 것만으로 +0.66%p였으니, 오차가 덜 겹치는 모델이면 더 클 수 있습니다.
- 평가·추론은 bf16 지원 GPU에서 — 같은 어댑터가 Colab fp16에서 0.8818, 로컬 bf16에서 0.8933이었습니다.
